§2 DESIGN CALLS
DOCTRINE IS CLASSES, NEVER SHIPS
A template row is (hull class, count, formation, stance) and nothing else — no ship ids, so a template survives every ship in it dying and deploys at any station with the inventory. Binding to real hulls happens at deploy, in roster order, by the same one-answer rule CARGO's fill uses. Squadron names are client-side, exactly as ADR-017 ruled for wing names: the server never learns what LANCE means.
ALL-OR-NOTHING, MADE LEGIBLE
The rule is upstream's; the screen's job is its cost. DEPLOY disabled names the exact shortfall per squadron (disabled-with-a-reason, the armed-verb rule again), and no partial-deploy affordance is drawn — offering "deploy 12 of 13" would be the screen overruling the design it implements.
SQUADRON = ROSTER ROW, 1 : 1
≤16 squadrons is not an arbitrary cap — MAX_ROSTER_ROWS is 16, and a deployed template lands on the tactical roster row for row, names and all. One number, two surfaces, no mapping layer; the doctrine you wrote is the fleet you fly.
ANNOUNCED, NOT SILENT
FleetAssembly's rule, drawn: assembly is a grid-visible state with the 15 s undock-protection window running, shown to the deployer exactly as others see it. A screen that hid the announcement would train players to believe deploys are private, and the first ambush would teach them otherwise.
THE CAP IS PERMANENT CHROME
13/64 sits beside the template name at all times — ADR-005's command ceiling is a fact a doctrine author designs against, not an error to discover at the button. The bar fills as squadrons grow; a template over the cap cannot be saved, and the row that breaks it says so.
A FULL-SCREEN SURFACE, NOT A TAB
Doctrine is not a station service — a template exists everywhere, so this is a surface on ADR-020's stack (TACTICAL ⇄ FLEET, ◀ back is the one mechanism), with the deploy target chosen inside it. The hangar keeps composition-now; entry points are the hangar header and the menu.
§3 DELIBERATELY ABSENT · OPEN
ABSENT BECAUSE THE DESIGN SAYS SO
▸ No ship-level assignment — roster order binds hulls to squadrons; hand-picking ships would make the deploy a function of clicks, and every one-answer rule in this corpus refuses that.
▸ No partial deploy — the all-or-nothing rule is the design, not a limitation to soften.
▸ No reserved hulls drawn — Fighter and Cruiser have hasContent false; a doctrine row for a hull that cannot exist would be the screen inventing content.
▸ No cross-station union — a template deploys from one station's roster. Pooling two stations' hangars would teleport the hauling game away.
OPEN — RULINGS THE FLEET ADR NEEDS
▸ Template storage — account-side (shown: "templates follow the account") or device-local. The third screen to ask 07h's question; it deserves one answer.
▸ Deploy while ships are damaged — does a hull with a worn gauge count against NEED? Proposed: yes, with the row noting it — repair-by-absence makes it moot at a station, but remote deploys will ask.
▸ Corp doctrine sharing — a shared template library is the obvious corp feature and a real design (permissions, versioning). Named so it is staged, not discovered.
▸ Defaults vs the wheel — squadron stance/formation seeds must use the same option lists OrderKinds reports, or a template could author a posture no order can carry. Wants a test, not just agreement.

The debug HUD has exactly one line of authority behind it: 01 §5's Telemetry.h says NEURON_COUNTER and NEURON_SPAN feed /metrics on the server and "the debug HUD" on the client. That is the whole specification. F11 asks whether it ships in release for ops value or is dev-only — and the register notes the answer decides whether it holds a share of the 0.50 ms screens allowance or none.

▶ PROPOSED ANSWER TO F11 — REFRAME IT
F11 is posed as a binary, and both answers are wrong. The ops value F11 wants does not require the HUD to ship — it requires the data to ship. A dump verb writes a trace from a real device at zero budget cost, no screen, and no attack surface, which is the same move 04 §8.2 made for the server with DumpDiagnostics. So: ship the dump unconditionally, ship a thin counters strip in release behind a setting, keep the full overlay dev-only. Three tiers, one of which answers F11's ops case without a pixel.

Tier 3 is the one that matters and the one nobody asked for. A player reporting "it stutters in big fights" currently sends a screenshot of a stutter, which contains no information. A dump verb sends a frame histogram, the budget table, network quality and the drop counters — the same payload DumpDiagnostics gives an operator on the server, from the device where the problem actually happened. It costs nothing per frame because it writes what the rings already hold.

Tier 1 is deliberately not a smaller Tier 2. It is a different instrument: every number in it is one a support conversation needs, and none of it is a number only an engineer can act on. Per-system costs, draw-call counts and allocator arenas are Tier 2 not because they are expensive to draw but because a player reading them learns nothing and a red-team reading them learns something.

§4 THE OBSERVER PROBLEM it runs on the thread it measures, and it must say so
WHY IT CANNOT HAVE A THREAD
01 §1.2 gives the client eight lanes and §2.4 spends all eight — Main, Game, Render and five workers. RegisterExternalThread() fails when lanes are exhausted, and the server's table budgets sixteen lanes for fifteen threads plus one spare while the client's has none. R2 F11 names the debug HUD as the first casualty of that, by name.
So the HUD samples the per-thread SPSC rings Telemetry.h already provides and drains them on the game thread once per frame. The drain is bounded by ring capacity, not by event count — it drops on full rather than growing, which is the only way a telemetry system stays inside a fixed budget under exactly the load that makes it interesting.
TWO HONESTY RULES THAT FOLLOW
1 · It reports its own cost as a line item. The observer effect cannot be removed, so it is displayed: UI 0.44 / 0.70 ◦ dbg 0.03. A reading that silently includes the instrument is a reading an engineer will chase for an afternoon.
2 · It shows its drop counters. When a ring overflows the HUD says how many samples it lost. A telemetry surface that quietly discards data under load is worse than none — it produces confident graphs of the frames that went well.
Both are why Tier 3's dump is the trustworthy artefact: it is written from the same rings with no drawing at all, so it carries no instrument cost to subtract.

§6 WHAT F11 DECIDES, AND WHAT STAYS OPEN
PROPOSED FOR RATIFICATION
▸ Tier 3 ships unconditionally in every build. It is the ops answer, and it needs no screen.
▸ Tier 1 ships in release, off by default, behind a Diagnostics section in §4.10 — which gives settings the sixth section 07h §6 anticipated.
▸ Tier 2 is dev-only and compiled out, not hidden. A shipped binary should not contain a surface that prints per-system costs.
▸ No new gesture. 03 §9.2 is normative and this screen does not earn a gesture-table amendment: the toggle is a setting, plus an F-key where a keyboard exists.
▸ Tier 1 shows only fields the viewer already holds — never a world-truth count. See right.

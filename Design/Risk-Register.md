# Risk Register

**Status:** Session output 2026-08-17 · R14 added 2026-08-18; R2/R5/R8/R11/R14 annotated and
**R6 marked realised** after S6; **R1 and R9 annotated after S9.** Top technical risks, each
with mitigation already wired into the ADRs/build order (referenced), plus its
early-validation point. Review at each milestone (M0/M1/MVP).

A risk that has actually fired is marked **🔥 realised** with what happened. That is the
useful part of a register: not the list of things that might go wrong, but the record of which
guesses were right.

| R6 | 🔥 **realised (twice, at S6)** — **Formation/steering feel** — servo oscillation, station fighting, straggler deadlocks make the one MVP mechanic feel bad | Med | Med | Arrival-slowdown steering with class clamps, stations non-overlapping by construction, leg completion tolerance + straggler timeout (ADR-005); envelope tests pin turn radius/overshoot | S6 envelope suite; S10 "preview equals outcome" test; tuning constants isolated in `ShipClassTable`. *As of S9 the "preview equals outcome" claim is structural rather than a test to write: the client's footprint calls `SolveFormation` through the seam — the same function, on the same quantised leg, with the same sort by ascending `ShipId` — so a preview that differed from the outcome would need the two to disagree about their own inputs. What S10 still has to prove is that the arrangement **fits**: the print's own open question is what the puck should do when a station lands inside a gate or another fleet.* **Both failures this risk predicted fired in S6, and neither was visible in the source.** *(1)* A hull's turn radius at cruise is `speed / turnRate` — 477 m for a Battleship — so a target sixty metres astern sits inside the circle it can turn on: the ship held its speed, swept past, and came round again, **three laps and a hundred seconds of simulated time to travel sixty metres.** Fixed by bounding speed at `omega·distance/(2·error)`, chosen by measuring four candidate limits across five hulls and five geometries. *(2)* The textbook braking curve `sqrt(2as)` is achievable only in continuous time; stepped at 20 Hz a ship sits above it, covers more ground per tick, and falls further behind — compounding all the way in. An Interceptor arrived 1.2 m out still doing **38 m/s** and settled 5.9 m past its target. Fixed with the discrete solution. **The lesson is the mitigation:** the envelope suite did not prevent either bug, it *found* both — the register's value here was predicting where to point a harness. |

## Standing spikes (cheap, do early, answer one question each)

1. **Loopback heartbeat under debugger** (S4): does breaking in the IDE wedge either side?
   Expected: no — transport tolerates stalls; verifies R5 posture. *Still to run: it needs a
   debugger and a person. The automated half (`selfTest`) passes.*
2. **Replay-hash across Debug/Release** (S6): confirm hashes *differ* across configs is
   acceptable and documented (same-binary scope, ADR-005 §6) — prevents a false alarm later.
   *Still to run: CI builds Debug only, so the two configs have never been compared. The suite
   that would answer it exists as of S6; it needs a Release build and one comparison.*
3. **1,024-instance draw** (after S5): 1,024 `InstanceRecord`s through the opaque pass —
   validates the corpus entity cap costs nothing on the render side (it shouldn't, instanced).
   *Still to run: needs a GPU. The instance path it would exercise has been in the tree since
   S5 and the scene is now built through the `WorldView` seam, so the test is a scenario rather
   than a code change.*
4. **Schannel QUIC availability** (before S13): one-liner msquic `QuicOpen` + listener on the
   dev/CI images — surfaces the OS-dependency question while there's slack, not during S13.
5. **Config-by-directory in CI** (with S2b): confirm a runner can select the self-test
   configuration purely by its working directory — this is the workflow that replaced flags,
   so it is worth exercising once before the build depends on it.

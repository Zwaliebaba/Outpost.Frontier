installation and the [reference build](reference-build.md) (work package
P0.3). Fill in **Value** and set **Status** to `known`. Quote file contents
exactly. Do not paste licensed content beyond the value itself.

Paths are relative to the repository root, laid out as in section 3 of the
reference-build guide.

and the installation's `DATA` in `outdir\data\`. `EXE\` below means the
INI files in `outdir\`, `DATA\` means `outdir\data\`.

| F15 | What made the compiled `.thn` chunks, and do they decompile to source that compiles back to them? | `cargo xtask thn-decompile outdir\data <out folder>`, and the round-trip test in `xtask/src/thn` | P4.14 | Lua 3.2 chunks without debug information (source name empty, no line or local records), numbers as text. Every chunk is straight-line code using 15 opcodes: `PUSHNUMBER`, `PUSHNUMBERNEG`, `PUSHCONSTANT`, `GETGLOBAL`, `CREATEARRAY`, `SETLIST`, `SETMAP`, `SETGLOBAL` (byte and word forms), `ADDOP` and `ENDCODE`. They hold no jumps, calls, functions or locals. The compiler was not the one in `CppSource`: no chunk stores a number twice, and numbers are reused up to 4,226 constants back, where `lparser.c` (as stock Lua 3.2) searches only the last 20. Numbers were printed by the MSVC `%.16g` with three exponent digits, rounding to 17 digits and then half up to 16 (`0.99999` is stored as `0.9999900000000001`). All 1506 chunks decompile to source that compiles back byte for byte. For 3 constants (`±0.0007780000000000001`, `±0.0007200000000000001`) the stored text reads back one unit in the last place above the value printed, so the source says `0.000778` and `0.00072`, and the tool reports them. Collected on 2026-11-17 | known |
| F17 | Do the system solars get a faction when the data loads? | `Common/common_cobjdb.cpp` (`LoadOneObjectSection`), `Common/common_dataconfig.cpp`, `OutpostFrontier.ini` `[Data]`, `DATA\UNIVERSE\SYSTEMS`; `Content/SystemInfo.cpp:313-380`, `Content/NpcCreate.cpp:70-104` | P3.3 replication, P3.4–P3.7 (Content) | Not when the data loads, but from Content when each system loads, before any player's creates. The data load sets none, for two reasons, in the reference and in the port: (1) `LoadOneObjectSection` sets the vibe's affiliation from a `group` key, but the system files name a solar's faction with `reputation` (2,124 uses in the 51 files under `UNIVERSE\SYSTEMS`, no `group` in `UNIVERSE`); (2) `[Data]` reads `universe` (line 85) before `groups = InitialWorld.ini` (line 187), so the registry is empty when the system files' vibes load. Content's SpaceSupport fully loads the system's record on `SystemLoaded` (`FSystemInfo::LoadFull`): it reads the system file's `[Object]` sections again (`LoadSolarNpcs`), and each named object with a `reputation` becomes a solar NPC whose reputation handle gives the nickname's vibe that faction (`pub::Reputation::GetReputation`, `SetAffiliation`). So `SETREPUTATION` at `add_player` carries the faction. On the shipped data 1,977 of the 2,119 solar NPCs of the 53 systems take one. Known from the code; the reference is not changed (the owner's decision, 2026-11-21; record 0008 question 5). The port does the same since P3.4d (`game-logic::content::solar_npcs`), and the data job compares it with the oracle (`content_solar_npcs`, `dump content_systems`) | known |
